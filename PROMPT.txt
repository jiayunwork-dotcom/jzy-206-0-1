水务公司的设备科要按季度上报泵站和加药系统的可用度。每台设备的故障、维修开始、维修结束、计划检修都记在维修工单系统里，但工单经常补录、改时间，有的维修单一直没关。季度末科员导出工单，在表格里拼出每台设备的运行和停机区间，算平均无故障时间、平均修复时间和可用度，再按系统结构（几台泵并联、后面串一套加药）算整条线的可用度。每季度都要花一周，数字还经常和上季度报的对不上。我是科里负责信息化的，想做一个后端服务来做这件事。

输入是工单事件流：每条事件带事件编号、设备、时刻和类型（故障、维修开始、维修结束、计划检修开始与结束、事件作废）。服务从事件推出每台设备的状态时间线：运行、故障待修、维修中、计划检修。事件会晚到、会重复（同编号只算一次）、会被作废或更正时刻；任何时候的结果都必须和“把当前有效事件按时刻排序后从头处理”一致。时间线出现矛盾（例如故障未结束又报一次故障、维修结束早于维修开始）时，不要静默修复，要把矛盾列出来，并按你定的规则给出一个确定的处理，规则写进文档。

统计：给定一个时间窗口，为每台设备估计平均无故障时间和平均修复时间，以及稳态可用度。窗口边界会截断正在进行的运行区间或维修区间，窗口结束时还没关闭的维修单也是截断数据。这些截断区间怎么纳入估计（直接丢弃、按截断长度计入、或按删失数据处理），直接影响结果偏高还是偏低，由你选定并说明，测试中用一组构造数据展示你的做法与“直接丢弃”的差别。计划检修时间是否计入停机，按设备类别可配置。参考值：平均无故障时间 900 小时、平均修复时间 100 小时，稳态可用度为 0.9。

系统可用度：系统结构是一张可靠性框图，由串联、并联和“n 中取 k”组合嵌套而成，叶子是设备。结构有版本，某段时间改了工艺（比如新增一台备用泵），之后的时段按新结构算。参考值：三台可用度都是 0.9 的设备组成“3 中取 2”，系统可用度 0.972；两台串联为 0.81；两台并联为 0.99。跨越结构变更的统计窗口，要按各结构生效的时长分段计算再合成，合成方式写清。

查询要支持“截至某个时点所掌握的数据”：例如按上季度报表日那天已经入库的事件重算上季度，结果要与当时报出的数完全一致；再按今天的全部事件重算同一季度，给出两者的差异以及造成差异的事件清单。两个班组同时提交同一台设备的事件，结果与按时刻顺序逐条处理一致。服务重启后从事件存储恢复。

需要成立：同类设备串联 n 台的可用度等于单台的 n 次方，并联 n 台等于一减去不可用度的 n 次方；可用度在 0 到 1 之间；某设备的事件全部作废后，它恢复为整个窗口都在运行；把整个事件流的时间整体平移，统计结果不变；框图中把两个并联分支互换，结果不变。

接口：设备与类别维护、事件提交（单条和批量）、设备时间线查询、矛盾清单、窗口统计、框图的版本维护、系统可用度查询、按时点重算与差异对比。拒收：“n 中取 k”里 k 大于 n 或不为正、框图引用不存在的设备或出现同一设备在同一结构里重复、窗口结束早于开始、事件类型未知、作废一条不存在的事件。

测试请覆盖：各参考值、串并联公式、平移不变、分支互换、作废回归、乱序与顺序一致、重复幂等、矛盾识别、截断处理与直接丢弃的对比、跨结构变更窗口、按时点重算的一致性与差异清单、并发提交、重启恢复。

用 Node.js 20 + TypeScript + Express 实现，事件及推导结果存 MongoDB 7。事件存储、时间线推导、矛盾检测、区间统计、可靠性框图、结构版本、按时点查询、接口按职责拆成多个模块。测试框架用 Vitest。镜像以 node:20-slim 为基础，compose 里配 mongo:7，报表系统会通过 HTTP 来取数。
